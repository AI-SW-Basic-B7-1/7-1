# 오류 처리 통합 검증

## 로컬 자동화

```bash
venv/bin/python -m pytest -q
node --test tests/frontend/*.test.mjs
bash -n scripts/ec2/check_error_logging.sh
```

Python 테스트는 임시 DB와 대체 AI 응답을 사용합니다. 실제 외부 AI 호출이나
EC2 서비스 상태를 검증하지 않습니다. 프론트 API 테스트도 화면 렌더링과는 별도입니다.

## 프론트 화면 점검

운영 서버 대신 로컬 테스트 환경의 네트워크 응답 대체 기능을 사용합니다.
로그인 후 기존 대화방을 열고 후속 질문을 전송하는 상황에서 `POST /api/chat`의
응답을 각 상태와 `{"detail":"테스트 안내"}`로 대체합니다.

| 상태 | 기대 동작 |
| --- | --- |
| 401 | 토큰 제거, 로그인 모달 표시, 질문 초안 보존, 이전 사용자 대화 화면 초기화 |
| 404 | 오류 안내, 로딩 종료, 질문 초안·기존 대화 유지 |
| 422 | 오류 안내, 로딩 종료, 질문 초안·기존 대화 유지 |
| 500 | 오류 안내, 로딩 종료, 질문 초안·기존 대화 유지 |
| 502 | 오류 안내, 로딩 종료, 질문 초안·기존 대화 유지 |
| 504 | 오류 안내, 로딩 종료, 질문 초안·기존 대화 유지 |

401에서 대화를 지우는 것은 계정 간 정보 노출을 막기 위한 동작입니다.
나머지 오류에서는 입력란·전송 버튼이 다시 활성화되고 응답 행의 대기 상태가
해제되는지 확인합니다. 안내는 토스트가 아닌 답변 행에 표시될 수 있습니다.
자동 POST 재전송이 없어야 하며, 재시도는 사용자가 선택해야 합니다.
서버 저장 후 통신이 끊긴 경우 재시도로 중복 저장될 수 있고 멱등성은 별도 과제입니다.

## 기동 실패

`tests/test_lifespan.py`는 초기화 실패가 기동 단계 밖으로 전달되고 초기화 완료
상태가 거짓으로 유지되는지 확인합니다. DB 마이그레이션 롤백은
`tests/test_database.py`에서 별도로 확인합니다. 운영 DB를 손상시키거나 경로 권한을
바꾸는 방식으로 테스트하지 않습니다.

## 교차 출처 제한

현재 프론트는 상대 API 경로를 사용하므로 같은 출처의 Nginx 배포에서는 CORS가
필요하지 않습니다. 로컬 확인 결과, 미처리 예외의 500 응답에는 요청 ID는 있지만
`Access-Control-Allow-Origin`이 없습니다. 프론트와 API를 서로 다른 출처로
분리하기 전에는 CORS를 전역 오류 응답까지 적용하도록 구성하고 허용·비허용
출처, 500 응답과 요청 ID 노출을 추가 검증해야 합니다.

## 검증 상태

- Python 자동화: 실행 결과를 PR에 기록합니다.
- 프론트 API 테스트: Node.js가 있는 환경에서 실행해야 합니다.
- 실제 브라우저 화면: 위 시나리오로 별도 확인해야 합니다.
- EC2: `docs/request_logging.md`의 읽기 전용 점검 절차를 사용합니다.
- 로그 마스킹: 애플리케이션 로거만 적용되며 Uvicorn·Nginx는 별도 점검 대상입니다.
